## 实施进度（2026-07-14）

里程碑一的代码部分已经完成首轮实施：

- Redis 幂等键已拆为带 owner token 的短租约执行锁，正常路径安全释放，硬崩溃依赖 TTL 恢复；

- `.env.example` 已替换为占位符，`.env` 已加入忽略规则并停止 Git 跟踪；

## 1. 当前项目定位

AdAgentFlow 已经具备多 Agent 长任务系统的主要工程骨架：

- 多 Agent 串行工作流；
- FastAPI 异步任务入口；
- RabbitMQ Worker 消费模型；
- Redis 幂等控制；
- PostgreSQL 状态持久化；
- 任务与节点状态机；
- JSON Schema 校验和自动修复；
- 质量评估、失败重试、死信接管；
- Trace、指标、Dashboard、测试和部署文档。

项目下一阶段不应继续堆叠大量新功能，而应集中完成三个目标：

1. 让核心可靠性链路真正闭环；
2. 让测试结果能够证明真实实现，而不只证明 Mock；
3. 让文档、数据和项目表述与实际能力保持一致。

## 3. P0：立即处理的工作

### 3.1 凭证与仓库安全

- [ ] 立即轮换当前仓库中出现过的 LLM Token；
- [x] 停止跟踪 `.env`，只保留不含真实值的 `.env.example`；
- [x] 将数据库、RabbitMQ、Langfuse 等默认密码改为占位符或环境变量；
- [ ] 检查 Git 历史中是否仍包含凭证，必要时清理历史；
- [ ] 增加基础 Secret Scanning，例如 Gitleaks；
- [ ] 确保日志、Trace 和死信记录不会保存完整 Token 或敏感请求头。

### 3.2 重新定义幂等语义

当前单个 24 小时 Redis Key 同时承担执行锁和去重标记，容易阻断正常重试。

- [x] 区分“正在执行锁”和“节点已成功完成标记”；
- [x] 执行锁增加唯一 owner/token，避免误释放其他 Worker 的锁；
- [x] 使用安全的比较并删除逻辑释放锁；
- [x] 节点成功后写入完成标记，重复消息根据数据库状态直接跳过；
- [x] 节点失败、取消或异常退出后允许重新执行；
- [ ] 明确锁租约、续约和超时恢复策略；
- [x] 死信恢复前清理或重建相关幂等状态；
- [x] 增加重复投递、锁过期和 Worker 崩溃测试。

### 3.3 修复消息 ACK/NACK 语义

- [x] Worker 不再吞掉所有 `execute_step` 异常后直接 ACK；
- [ ] 区分可重试异常、不可重试异常和坏消息；
- [x] 可重试基础设施异常应 NACK/requeue 或进入受控重试队列；
- [ ] 无法解析的消息应记录原因并进入死信，而不是静默丢弃；
- [x] 明确数据库提交、下一节点发布和当前消息 ACK 的先后关系；
- [ ] 为消息增加稳定的 `message_id`、`correlation_id` 和投递次数；
- [ ] 验证 Worker 在处理前、处理中、提交后退出时的恢复行为。

### 3.4 将重试调度持久化

- [x] 不再使用单纯的 `asyncio.create_task + sleep` 承担延迟重试；
- [x] 使用 RabbitMQ TTL + DLX、Delayed Message Exchange 或数据库调度表；
- [x] Worker 重启后，未到期重试仍然能够继续；
- [ ] 增加指数退避、最大延迟和随机抖动，避免重试风暴；
- [ ] 按错误类型判断是否值得重试；
- [x] 记录每次重试的独立执行信息和失败原因。

### 3.5 完成 Repair Agent 闭环

- [x] 为 Repair 定义明确的输入、输出和执行记录；
- [x] 修复结果写回目标节点的新版本，而不是直接结束整个任务；
- [x] 标记依赖旧结果的下游节点失效；
- [x] 从目标节点之后重新执行必要步骤；
- [x] 保留原始结果、修复结果和修复原因，方便审计对比；
- [ ] 限制修复次数，避免无限循环；
- [ ] 无法自动修复时进入人工审核或死信；
- [ ] 增加脚本修复、分镜修复和修复失败的端到端测试。

### 3.6 修复质量评估反馈链路

- [x] 评估不通过时允许合法重跑 `script_generation`；
- [x] 不让旧的成功状态和幂等标记阻断重新生成；
- [x] 重跑脚本后使分镜、素材和旧评估结果失效；
- [ ] 明确低分、高风险和一般问题分别进入重试、修复还是人工审核；
- [x] 为评估—修复循环设置次数上限；
- [ ] 校验 `passed`、`score` 和 `risk_level` 的逻辑一致性。

## 10. 建议里程碑

### 里程碑一：可靠性闭环

完成条件：

- 凭证已轮换并移出仓库；
- 重试不会被幂等键阻断；
- Worker 异常不会被静默 ACK；
- 延迟重试在 Worker 重启后仍存在；
- Repair 能写回结果并继续工作流；
- 质量评估反馈能够触发合法重跑。

### 里程碑二：真实链路验证

完成条件：

- PostgreSQL、Redis、RabbitMQ 集成测试稳定运行；
- 至少完成一轮故障矩阵实验；
- API 到最终结果的端到端测试通过；
- 最终输出包含脚本、分镜、素材和评分；
- Docker Compose 可以正常启动和扩展 Worker。

### 里程碑三：可展示版本

完成条件：

- README 描述与真实实现一致；
- 有可复现的测试和压测报告；
- 有清晰架构图、故障时序图和 3～5 篇 ADR；
- 可以现场演示正常执行、失败重试和死信恢复；
- 能回答核心技术选型、故障窗口和项目限制。

### 里程碑四：持续演进

完成条件：

- 接入真实小规模用户或实际商品数据；
- 根据真实反馈优化评测集和 Prompt；
- 建立成本、质量和可靠性的持续对比；
- 只在真实需求出现时增加企业级能力。

## 11. 当前阶段的非目标

## 12. 最终验收标准

当下面的问题都可以通过代码、测试或实验直接回答时，项目就达到了很有竞争力的实习/校招展示水平：

- Worker 在任意关键阶段退出，任务是否会丢失？
- 消息被重复投递，业务结果是否仍然等价一次？
- 数据库成功但消息发布失败，系统如何恢复？
- 重试为什么不会被幂等机制阻断？
- Repair 修改上游结果后，下游数据如何失效和重建？
- 最终用户在哪里取得完整生成结果？
- 系统真实瓶颈在哪里，数据如何得出？
- 一次任务的质量、延迟和成本分别是多少？
- 哪些能力已经验证，哪些仍然只是设计方案？
- 为什么当前架构适合这个项目，而不是单纯为了复杂而复杂？

项目完成这些工作后，不需要继续扩大范围。它的核心价值应当是：用一个范围受控的多 Agent 广告生成场景，完整展示异步长任务在幂等、重试、恢复、修复、观测和验证方面的工程设计。
