# ADR-0002：RabbitMQ 工作流与 Ray 的边界

- 状态：已采纳
- 日期：2026-07-14

## 背景

候选方案包括直接 RabbitMQ、Celery、Kafka、Temporal/LangGraph，以及 Ray。当前核心问题是分钟级 Agent 任务的可靠派发、延迟重试、死信和异构 Worker，而不是大规模分布式计算。

## 决策

当前继续使用 RabbitMQ + 显式状态机 + PostgreSQL。RabbitMQ 提供路由、ACK/NACK、TTL/DLX 和积压缓冲；状态机和执行历史由本项目掌控，便于展示故障语义。

Ray 暂不接入。Ray 更适合大量并行 Python 计算、GPU Actor、模型服务和数据处理；它不能自动替代业务持久化、Outbox、幂等和可恢复工作流。只有出现 GPU 常驻模型、并行素材处理或明显的计算调度瓶颈时再做独立 PoC。

Temporal 适合未来更长、更复杂、需要 durable timer/补偿/人工等待的流程，但当前引入会显著增加运行和学习成本。Kafka 在事件回放和超高吞吐上更强，但不符合当前任务队列规模。

## 代价

- 自己维护状态机、补偿和执行历史；
- RabbitMQ 不是长期事件日志；
- 工作流复杂度继续上升时，应用层编排代码会变重。

## 重新评估条件

- 单工作流出现大量并行分支、跨天等待或复杂补偿；
- GPU/CPU 分布式计算成为主要耗时；
- 需要事件长期回放、多个独立消费者或吞吐量级显著提高。
