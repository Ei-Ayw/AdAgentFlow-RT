## 但现在还有几个必须修的问题

### 1. README 里的 pytest 还是错的

README 里写：

```bash
.venv/bin/python -m pytest -q tests/test_harness.py tests/test_contractual_runtime.py tests/test_state_machine.py
```

但包里没有 `tests/` 目录。我实际跑会报：

```text
ERROR: file or directory not found: tests/test_harness.py
```

所以 README 不能再写 pytest smoke tests passing。

建议改成：

```bash
PYTHONPATH=. python -m compileall -q app experiments scripts
PYTHONPATH=. python -m experiments.harness.validate_suite \
  --suite-config experiments/harness/configs/suite_main_compressed.yaml
PYTHONPATH=. python -m experiments.harness.audit_results \
  --summary experiments/results/main/real_full_v2/summary.json \
  --require-external-main --require-agentchange
```

除非你真的补 `tests/`，否则不要写 pytest。

---

### 2. `finalize_submission.sh` 现在不可移植

README 说：

```bash
./scripts/finalize_submission.sh --local-only
```

但我实际跑会挂：

```text
scripts/finalize_submission.sh: line 58: .venv/bin/python: No such file or directory
```

原因是脚本硬编码了 `.venv/bin/python`。投稿 artifact 里最好不要假设 reviewer 已经有 `.venv`。

建议把脚本开头改成：

```bash
PYTHON_BIN="${PYTHON_BIN:-python}"
```

然后所有：

```bash
.venv/bin/python -m ...
```

改成：

```bash
"${PYTHON_BIN}" -m ...
```

README 里写：

```bash
PYTHON_BIN=python ./scripts/finalize_submission.sh --local-only
```

这样更稳。

### 4. 论文里还在说 “benchmark-native scorer”，这个要改

你现在正文 Table 1 附近写：

> “Fixture” is the benchmark-native scorer

但 README 又说：

> scoring is fixture-backed and assertion-based; it is not a full benchmark-native simulator rerun

这两个说法冲突。

建议全文统一成：

> fixture-backed assertion scorer

不要再写 “benchmark-native scorer”。否则 reviewer 会问：你到底有没有跑 tau3 原生 simulator？如果没有，就不要用 benchmark-native 这个词。

Table caption 建议改成：

> “Fixture” is the fixture-backed assertion score derived from public benchmark metadata, not a full benchmark-native simulator rerun.

### 5. Table 2 的 “Recovery actions” 数字不可信

Table 2 现在写：

| Method      | Recovery actions |
| ----------- | ---------------: |
| Vanilla     |             0.00 |
| Retry-only  |             3.00 |
| Schema-only |             1.00 |
| Full        |             1.40 |

但 `runtime_stability_metrics.csv` 里并没有一个直接对应这个 1.40 的字段。当前 CSV 里 full 的主要值是：

```text
retry_amplification_factor = 1.0
extra_llm_calls = 2.0
trace_event_count = 6.0
```

而从 `recovery_action_counts` 算，full 的 recovery actions per task 大约是 2.0，不是 1.40。

所以 Table 2 这里很容易被认为是手工遗留数字。建议二选一：

第一种，把这一列改成 `Trace events/task`，用 `trace_event_count`：

| Method      | Trace events/task |
| ----------- | ----------------: |
| Vanilla     |              0.00 |
| Retry-only  |              0.00 |
| Schema-only |              0.00 |
| Full        |              6.00 |

第二种，把这一列改成 `Extra LLM calls/task`，用 CSV 里的 `extra_llm_calls`。

不要再写 “Recovery actions = 1.40”。

### 6. Figure 6 和 Table 1 的 cost 口径容易冲突

Table 1 写 weighted cost：

| Method      | Weighted cost/success |
| ----------- | --------------------: |
| Retry-only  |                 37.19 |
| Schema-only |                 16.55 |
| Full        |                 16.50 |

但是 Figure 6 看起来 full 约 26，schema-only 约 22，retry-only 约 48。这个更像 nonzero-cell mean，不是 weighted value。

所以 Figure 6 必须改 caption：

> Nonzero-cell mean cost per successful task under fault injection.

或者重新生成一个 weighted cost bar chart，让它和 Table 1 完全一致。否则 reviewer 会觉得图表互相打架。
